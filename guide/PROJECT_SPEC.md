## 1. Architecture at a glance

```text
Officer enters Driving License number
            │
            ▼
   ┌─────────────────┐   GET /api/risk-profile/:license
   │ React frontend  │ ───────────────────────────────┐
   └─────────────────┘                                ▼
                                          ┌──────────────────────┐
                                          │ Express backend      │
                                          │ 1. validate license  │
                                          │ 2. MongoDB lookup ───┼──► MongoDB (customers)
                                          │ 3. preprocess/facts  │
                                          │ 4. ML score ─────────┼──► ml-service (FastAPI)  [mock until ML file arrives]
                                          │ 5. build indicators  │
                                          │ 6. LLM narrative ────┼──► LLM API (fallback template if it fails)
                                          │ 7. assemble response │
                                          └──────────────────────┘
```

Order matters: the ML model runs first (milliseconds), then the LLM writes the summary **using the model's score and top factors**. That way the summary and the score badge never contradict each other.

## 2. Key decisions

| Decision | Choice | Why |
|---|---|---|
| Repo layout | One monorepo: `backend/`, `frontend/`, `ml-service/`, `data/`, `docs/` | One repo for Antigravity to see; easy to demo |
| Backend | Node.js + Express + Mongoose | Your MERN stack |
| Serving the ML model | Small **Python FastAPI service** (`ml-service/`) | Node can't load `.pkl`/`.joblib` files. FastAPI is the simplest way |
| Before the ML file arrives | Backend runs with `ML_MODE=mock` (rule-based scorer with the **same response shape**) | You can build and test everything end to end today; the real model is a config switch later |
| Feature encoding | Lives **inside the ML pipeline** (teammate exports one sklearn `Pipeline`) | Train and serve encoding can never drift apart |
| Numbers vs narrative | Facts, severities and indicators are computed **in code**; the LLM only writes headline, narrative and recommendation | Makes the 85% accuracy target achievable and testable |
| LLM failure | Timeout 12s, one retry on invalid JSON, then a template-based fallback summary | The demo never shows an error because of the LLM |
| Speed target | Whole request under 20s (aim for under 6s) | Problem statement metric |

## 4. Contracts (do not change without updating all three layers)

### 4.1 Public API (frontend ↔ backend)

`GET /api/risk-profile/:licenseNumber`. License format: 15 characters, `^[A-Z]{2}\d{2}\d{4}\d{7}$` (state, RTO, issue year, serial). Normalise by uppercasing and stripping spaces and hyphens.

```json
{
  "customer": { "customerId": "CUST000041", "licenseNumber": "MH4720231551327", "name": "Aditya Gowda", "age": 23, "occupation": "salaried", "cityTier": "metro" },
  "vehicle":  { "category": "two_wheeler", "subtype": "sports_bike", "engineCc": 165, "ageYears": 2, "marketValueInr": 210000, "usage": "personal", "hasModifications": false },
  "insuranceHistory": { "isFirstTimeBuyer": true, "priorInsuranceYears": 0 },
  "risk": {
    "score": 69,
    "tier": "high",
    "probabilities": { "low": 0.02, "medium": 0.21, "high": 0.77 },
    "modelVersion": "mock-rules-0.1",
    "topFactors": [
      { "feature": "vehicle_subtype", "value": "sports_bike", "impact": 0.24, "direction": "increases_risk" }
    ]
  },
  "indicators": [
    { "key": "vehicle", "title": "Vehicle type", "severity": "high",
      "fact": "Sports bike, 165 cc: bikes carry higher accident risk than cars",
      "sourceFields": ["vehicle.category", "vehicle.subtype", "vehicle.engine_cc"] }
  ],
  "summary": {
    "headline": "High risk: first-time buyer on a sports bike",
    "narrative": "…90 to 140 words…",
    "recommendation": "…1 to 2 sentences…",
    "source": "llm"
  },
  "meta": { "isFallbackSummary": false, "mlMode": "mock", "latencyMs": { "db": 12, "ml": 4, "llm": 2100, "total": 2200 } }
}
```

- `indicators` always has **5 items** in this order: `vehicle`, `claims`, `violations`, `driver`, `history` (see the five parameters we agreed on). `severity` is `low | medium | high | info`.
- Errors: `{ "error": { "code": "LICENSE_NOT_FOUND", "message": "…" } }` with codes `INVALID_LICENSE_FORMAT` (400), `LICENSE_NOT_FOUND` (404), `ML_UNAVAILABLE` (503), `INTERNAL` (500).
- `GET /api/customers/:licenseNumber` returns the raw stored record (debugging only).

### 4.2 ML service (backend ↔ ml-service)

`POST /predict`, body `{ "record": <nested customer record, no label> }`.

```json
{
  "risk_score": 69,
  "risk_tier": "high",
  "probabilities": { "low": 0.02, "medium": 0.21, "high": 0.77 },
  "top_factors": [
    { "feature": "vehicle_subtype", "value": "sports_bike", "impact": 0.24, "direction": "increases_risk" }
  ],
  "model_version": "rf-2026-10-05"
}
```

`GET /health` returns `{ "status": "ok", "model_version": "…" }`. `feature` uses the CSV column names (`vehicle_subtype`, `claim_history_claims_last_5y`, …). The mock scorer must return exactly this shape.

### 4.3 LLM output (must be valid JSON)

```json
{ "headline": "≤ 12 words", "narrative": "90-140 words", "recommendation": "1-2 sentences" }
```

The LLM receives the facts, indicators, score, tier and top factors, and may **not** introduce any number or claim that is not in its input.

### 4.4 Feature → indicator mapping (`featureMap.js`)

| Indicator | Model features that map to it |
|---|---|
| `vehicle` | `vehicle_category`, `vehicle_subtype`, `vehicle_engine_cc`, `vehicle_has_modifications`, `vehicle_vehicle_age_years`, `vehicle_fuel_type`, `vehicle_market_value_inr`, `vehicle_usage`, `vehicle_annual_km` |
| `claims` | every `claim_history_*` |
| `violations` | `risk_factors_traffic_violations_3y`, `risk_factors_license_suspended` |
| `driver` | `driver_age`, `driver_driving_experience_years`, `driver_occupation`, `driver_marital_status`, `driver_city_tier`, `risk_factors_night_driving_pct`, `risk_factors_telematics_score` |
| `history` | every `insurance_history_*`, `risk_factors_ncb_percent`, `risk_factors_previous_policy_lapse` |

### 4.5 How freshers are treated (for the docs and the prompts)

A first-time buyer has 0 claims and 0% NCB because there is **no data**, not because they are safe. The system must say so ("no prior history; assessed mainly on vehicle and driver profile") and must never call a fresher's record "clean".

## 5. Database setup (MongoDB)

**Option A: MongoDB Atlas (recommended, no install)**
1. Create a free **M0** cluster at cloud.mongodb.com.
2. *Database Access* → add a database user (username + password).
3. *Network Access* → add your IP (for a hackathon demo `0.0.0.0/0` is fine; remove it afterwards).
4. *Connect → Drivers* → copy the connection string. Put it in `backend/.env`:
   `MONGODB_URI=mongodb+srv://<user>:<password>@<cluster>.mongodb.net/insurance?retryWrites=true&w=majority`

**Option B: local**
1. Install MongoDB Community Server and start it (`mongod`).
2. `MONGODB_URI=mongodb://127.0.0.1:27017/insurance`

**Load the data** (after Prompt 1 creates the seed script):
```bash
cd backend
npm install
npm run seed          # loads data/customers_db.json, prints "Inserted 10000", creates the unique index
```
Alternative without the script:
```bash
mongoimport --uri "$MONGODB_URI" --collection customers --file ../data/customers_db.json --jsonArray
```
then in `mongosh`:
```js
db.customers.createIndex({ "driver.driving_license_number": 1 }, { unique: true })
```

**Verify** in mongosh or Compass:
```js
db.customers.countDocuments()                                                     // 10000
db.customers.findOne({ "driver.driving_license_number": "MH4720231551327" })      // Aditya Gowda
```

### Prompt 3: ML client with a mock scorer

```text
Read docs/PROJECT_SPEC.md, especially Sections 4.2, 4.4 and 8. Work only inside backend/.

The real ML model does not exist yet, so build the client so the switch is one env variable.

1. services/mockScorer.js: a deterministic, rule-based scorer taking the nested record and returning
   the exact response shape from Section 4.2 (risk_score 0-100, risk_tier, probabilities,
   top_factors sorted by impact with 5 entries, model_version "mock-rules-0.1").
   Rules (points): base 18; vehicle category (two_wheeler +10, commercial +9, three_wheeler +6, car 0);
   subtype (sports_bike +9, cruiser +4, heavy_truck +6, bus +5, luxury +5, suv +2);
   city tier (metro +6, tier2 +3, tier3 0, rural -2); age <25 +14, <30 +6, >62 +5;
   experience <2 +10, <5 +4; modified vehicle +6; each claim +6 (max 5), each at-fault +4;
   each violation +3.5; license suspended +12; policy lapse +5; night driving pct * 0.15;
   NCB pct * -0.1. For first-time buyers multiply the vehicle points by 1.4 and add +5.
   Clamp to 0-100. Tier: <35 low, <60 medium, else high.
   Probabilities: a simple softmax-like spread centred on the tier.
2. services/mlClient.service.js: predict(record).
   ML_MODE=mock -> call mockScorer.
   ML_MODE=remote -> axios POST `${ML_SERVICE_URL}/predict` with { record }, 3000 ms timeout;
   on network error or non-2xx throw ApiError('ML_UNAVAILABLE', 503).
3. constants/featureMap.js: implement the table in Section 4.4 as a map from feature name to
   indicator key plus a helper featureToIndicator(feature). Also a label map from feature to
   human-readable text (e.g. vehicle_subtype -> "Vehicle subtype").
4. Unit tests: mock scorer returns the demo customers from Section 5 in a sensible order
   (sports-bike fresher high, clean hatchback owner low).

Acceptance: `npm test` passes; a small script printing the mock result for the 5 demo customers
shows tiers high, medium, high, low, medium.
```

### Prompt 4: Indicators, LLM, orchestrator, main endpoint

```text
Read docs/PROJECT_SPEC.md (all of Section 4). Work only inside backend/. Planning mode.

Build the full pipeline behind GET /api/risk-profile/:licenseNumber.

A. services/indicators.service.js: buildIndicators({cleanRecord, facts, ml}) returns exactly 5
   indicators in this order: vehicle, claims, violations, driver, history. Each has
   { key, title, severity, fact, sourceFields }. Severity and the `fact` sentence are computed
   in code with fixed rules (e.g. claims: high if >=3 claims or >=2 at-fault, medium if 1-2, low if 0
   and not a first-time buyer, "info" for first-time buyers with text "No claim history: first-time
   buyer, risk assessed on vehicle and driver profile"). Every number in `fact` must come from the record.
   Use ml.top_factors (via featureMap) to mark which indicators the model weighted most (add `modelWeight`).

B. services/llm.service.js: generateJson({ system, user }) that is provider-agnostic. Read
   LLM_PROVIDER, LLM_API_KEY, LLM_MODEL from env. Implement the provider I select in .env
   (default "gemini") via its official SDK or REST API. temperature 0.2, request JSON output,
   timeout LLM_TIMEOUT_MS (default 12000). Structure the code so adding another provider is one file.

C. prompts/summaryPrompt.js: build the system and user prompts.
   System rules: you write underwriting risk summaries for vehicle insurance; use ONLY the facts and
   numbers in the provided JSON; never invent or round numbers differently; if isFirstTimeBuyer is true,
   state that there is no prior history and that the assessment relies on vehicle type and driver
   profile, and never describe the record as "clean"; mention the risk tier and score; lead with the
   top 2-3 risk drivers; be neutral and professional; this is decision support, the underwriter decides.
   Output JSON only: { headline (<=12 words), narrative (90-140 words), recommendation (1-2 sentences) }.
   User prompt: the customer facts, the 5 indicators, risk score, tier and top factors.

D. Validate the LLM JSON with zod. On invalid JSON retry once; if it still fails, or on timeout or
   provider error, use services/fallbackSummary.service.js (template-based text using the same
   facts) and set summary.source = "fallback" and meta.isFallbackSummary = true.

E. services/riskProfile.service.js orchestrates: validate license -> findByLicense -> preprocess ->
   mlClient.predict -> buildIndicators -> LLM (or fallback) -> assemble the response EXACTLY as in
   Section 4.1, including meta.latencyMs for db, ml, llm and total (use utils/timer.js).
   Controller + route: GET /api/risk-profile/:licenseNumber.

F. Tests: run the service for the 5 demo customers with the LLM mocked; verify the response shape,
   5 indicators in order, and that fallback triggers when the LLM throws.

Acceptance: with a valid LLM key the endpoint returns a full response in under 8 seconds for all
5 demo customers; with an invalid key it still returns a response with summary.source "fallback".
```

## 7. When the ML file arrives

### 7.1 What to ask your teammate for (send her this list)

1. **`risk_model.joblib`**: one scikit-learn `Pipeline` (imputer + encoders + model) trained on the columns of `customers.csv`, so raw columns go in and predictions come out. If it is XGBoost/LightGBM, the pipeline should still include the encoding.
2. **`model_meta.json`**: `model_version`, class order, exact feature names and order, how the score is defined, training seed, Python and library versions, and metrics (overall accuracy, per-tier precision and recall, accuracy on first-time buyers).
3. **`requirements.txt`** from her environment (`pip freeze`). Model files often fail to load if the scikit-learn version differs.
4. **`sample_io.json`**: about 20 input records with her model's exact outputs, used as a parity test.
5. **Explanations**: SHAP values (TreeExplainer) so each prediction returns its top 5 factors. If she can't, a global feature-importance file is the fallback, but then the "key indicators" are the same for everyone.
6. **Score and tier consistency**: preferably a regressor for `label_risk_score` and a classifier for the tier probabilities. The backend then derives the tier from the score (`<35` low, `<60` medium, else high) so the two can never disagree. If she only has a classifier, use score = `round(100 × (0.5·P(medium) + 1.0·P(high)))`.
7. Make sure the training excluded `customer_id`, `driver_driving_license_number` and both label columns.

1. **Branch:** `git checkout -b feat/ml-integration`.

### 7.3 Common problems

| Symptom | Likely cause | Fix |
|---|---|---|
| `InconsistentVersionWarning` or unpickling error | Different scikit-learn/xgboost version from her environment | Install her exact versions from her `requirements.txt` |
| `columns are missing` or `unknown category` | Column names or order differ from training | Use `feature_names_in_`; ask her to set `handle_unknown="ignore"` on the encoder |
| Prediction fails on nulls | Telematics or months-since-last-claim missing | The pipeline needs an imputer, or use a model that handles NaN |
| Backend returns `ML_UNAVAILABLE` | Service not running or wrong port | Check `ML_SERVICE_URL` and open `/health` |
| Score says medium but badge says high | Tier and score computed separately | Derive the tier from the score in one place |
| Summary contradicts the score | LLM run before the ML result | Keep the order in Section 1: ML first, then the LLM |
| Browser CORS error | Wrong `CORS_ORIGIN` | Set it to the frontend URL (for example `http://localhost:5173`) |

**If her model is exported as ONNX** you could skip the Python service and use `onnxruntime-node` inside Express. Ask before choosing this, because SHAP explanations are harder in that setup.
